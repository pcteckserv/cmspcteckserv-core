# Core 3.1.6 — atualizações de distribuições instaladas

A 3.1.5 congelava o lock do projeto, mas a distribuição instalada podia conter metadados diferentes e origens `path` que apenas existiam no computador de desenvolvimento. Isso podia provocar reposições de versões e reinstalações a partir de caminhos inexistentes. Repor apenas o atualizador 3.1.4 não elimina essas origens nem corrige a remoção, que também executava Composer diretamente.

`ComposerDeploymentTransaction` passa a construir a preparação a partir de `vendor/composer/installed.json`. Mantém versões e requisitos efetivamente instalados. Para packages `path`, prepara arquivos ZIP dos ficheiros que estão em `vendor`, sem consultar o diretório de desenvolvimento nem os manifests de fontes mais recentes. Os arquivos ficam numa origem relativa e reutilizável em `storage/app/composer-snapshots`. A origem é identificada como snapshot para conservar a leitura das versões dos plugins e o bloqueio de atualização de um Core snapshot por simples alteração de versão.

O mesmo procedimento é usado na remoção. Apenas o pacote escolhido sai dos requisitos; as restantes versões ficam congeladas. Se outro pacote instalado ainda o exigir, a remoção é recusada antes da publicação. O inventário só é eliminado após sucesso; as tabelas e os dados do plugin são preservados. A remoção não executa migrations. O manifesto publicado deixa de listar repositórios locais inexistentes; as versões instaladas não são reduzidas para corresponder a um lock antigo. Antes de publicar, Composer valida também a coerência do manifesto final.

Mantêm-se preparação separada, manutenção durante a troca, cópia anterior e tentativa de reposição dos ficheiros. A base de dados não é revertida automaticamente. É necessário espaço para a preparação, PHP CLI, Composer compatível e ZIP. Um pacote sem ficheiros instalados identificáveis gera um erro antes da publicação. A preservação dos arquivos não é uma garantia contra interrupção do alojamento ou falta de disco.

`CompatibleCoreUpdater` conserva a API da 3.1.5 e delega no procedimento comum. O Starter CGLimpezas 0.0.8 carrega as duas classes novas enquanto não estão disponíveis no Core instalado. É necessário atualizar primeiro o Starter; publicar a tag do Core, por si só, não substitui o atualizador que já está a executar no alojamento.

A pesquisa e a apresentação de atualizações continuam limitadas aos plugins instalados e ativos. Não são alteradas outras funcionalidades do Core, a declaração das suas dependências, migrations ou os dados dos sites nesta entrega.

Validação: **252 testes do Core aprovados, 1297 asserções**. Os ensaios Composer reais incluem origens de desenvolvimento removidas, origem de deploy diferente no lock e no inventário, versão do Laravel instalada diferente da bloqueada, remoção bem-sucedida, dependentes que impedem remover, preservação do Core snapshot, modo sem dependências de desenvolvimento e reposição após falha. A execução do `composer install --dry-run` no resultado também foi verificada. A instalação local do CGLimpezas manteve o Core 3.0.1 e todas as dependências; **129 testes do site aprovados, 12 ignorados por exigirem MySQL isolado, 720 asserções**. O painel foi verificado em Chrome a 1440, 390 e 320 px.

O ensaio com a árvore completa da distribuição confirmou a resolução e preparação sem os caminhos antigos; a troca completa dessa árvore foi recusada pelo PHP no ambiente Windows de teste. Não é apresentado como um deploy completo aprovado nem como validação no alojamento Linux. As operações completas e a reposição são cobertas pelos ensaios Composer isolados. A nova versão deve ser confirmada no alojamento após instalar o Starter atualizado.
